# Где написано? для кейса Softline

Описание изменений под хакатон «ИИкузница»: ответы по регламентам ДБРЦТ, Дирекции ИБ и Технической дирекции со ссылкой на пункт, уточнение подразделения, письма в службу качества и дообучение по ответам экспертов. Документ описывает текущее состояние прототипа и его ограничения; готовым к промышленной эксплуатации он не является.

## 1. Что сделано

| Функция | Как работает | Где в коде |
|---|---|---|
| Стиль ответа | Короткая выжимка простым языком и отдельный блок «Где написано» с документом, номером пункта, цитатой и ссылкой `/doc/<документ>?p=<пункт>`: она открывает документ целиком и подсвечивает пункт. Проверка цитаты и чисел осталась: число, которого нет в пункте, скрывает формулировку модели и оставляет дословный пункт | `app/answer.py`, `app/llm/prompts.py`, `static/doc.*` |
| Уточнение подразделения | Если подходящие пункты есть у нескольких дирекций, бот спрашивает подразделение (не больше `CLARIFY_MAX` раз за сессию), запоминает выбор в сессии и ищет только в регламентах выбранной дирекции. «Не знаю» или вопрос про сравнение дают отдельные ответы по каждой дирекции со своими пунктами. Сроки не усредняются: ответы по дирекциям строятся независимо | `app/assistant.py`, `app/boxes.py`, `examples/boxes_softline.csv` |
| Письмо в службу качества | При отсутствии ответа, противоречии пунктов или низкой уверенности формируется письмо на `QUALITY_EMAIL`, сотрудник в копии. Без `SMTP_HOST` письмо сохраняется как `.eml` в `DATA_DIR/outbox` | `app/escalation.py` |
| Дообучение по ответу эксперта | Ответ из формы в админке, из `.eml` или по IMAP попадает в базу разъяснений; повторный похожий вопрос получает его с пометкой «Разъяснение службы качества». Регламенты не меняются. Счётчик повторов подсказывает, какие регламенты стоит пересмотреть | `app/faq.py`, `app/escalation.py` |
| Вне базы | Вопросы про маржу и премии, просьбы составить письмо или анализ, разговор не по делу получают отказ. Ссылка регламента на документ, которого нет в базе, называется прямо | `app/guard.py` |
| Глоссарий | `data/glossary.tsv` расширяет поисковый запрос (сокращение и расшифровка) и показывает расшифровки в ответе | `app/glossary.py` |
| Аналитика | Раздел в существующей админке: неудачные поиски, эскалации, повторы, популярные документы и пункты, время ответа, стоимость вопроса | `app/analytics.py`, `static/admin.*` |
| Устойчивость | Предохранитель вокруг LLM: после двух сбоев подряд на минуту запросы не ждут таймаутов. Если реранкер уверен в первом пункте (оценка не ниже `QUOTE_FALLBACK_SCORE`), а модель ответила «ответа нет», пункт показывается дословно | `app/llm/base.py`, `app/answer.py` |

Telegram-бот получил те же режимы: кнопки выбора подразделения, ссылки на документы (если задан `WEB_PUBLIC_URL`), сообщения об эскалации и разъяснениях.

Тестовый набор: `eval/test_questions.json` (31 вопрос, категории A–G) и `eval/conflicts.md` (расхождения между регламентами, найденные по тексту документов). Все ожидания в наборе построены по четырём выданным DOCX.

## 2. Запуск (PowerShell)

```powershell
cd D:\gde-napisano
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements-dev.txt
copy examples\boxes_softline.csv data\boxes.csv
copy examples\glossary.tsv data\glossary.tsv
# регламенты положить в data\docs, в .env задать значения (образец: .env.example)
.\.venv\Scripts\python.exe -m pytest
.\.venv\Scripts\python.exe -m uvicorn app.main:app_factory --factory --host 127.0.0.1 --port 8010
.\.venv\Scripts\python.exe -m bot
.\.venv\Scripts\python.exe scripts\eval_softline.py --docs data\docs --questions eval\test_questions.json --out eval
```

Python 3.11 или новее (закреплённые версии пакетов). Веб-интерфейс: `http://127.0.0.1:8010`, админка: `/admin` (токен `ADMIN_TOKEN`). Ключевые переменные: `LLM_PROVIDER`, `QUALITY_EMAIL`, `DEMO_USER_EMAIL`, `SMTP_*`, `IMAP_*`, `BOXES_CSV`, `GLOSSARY_TSV`; полный список с комментариями в `.env.example`.

## 3. Результаты прогона тестовых вопросов

Прогон `scripts/eval_softline.py` по четырём настоящим регламентам (679 пунктов) на сервере без GPU: 8 vCPU, 15 ГБ ОЗУ, модели поиска `multilingual-e5-base` и `bge-reranker-v2-m3`, LLM `qwen2.5:3b-instruct` через Ollama. Проверки автоматические и грубые (режим ответа, номер пункта, ключевые числа).

| Категория | Что проверяется | Прошло | Медиана, с | Максимум, с |
|---|---|---|---|---|
| A | прямые вопросы | 7/7 | 15,3 | 19,1 |
| B | нет в базе, письмо в службу качества | 5/5 | 9,0 | 24,1 |
| C | уточнение подразделения, затем «не знаю» | 6/6 | 31,2 | 49,2 |
| D | расхождения и отсутствующие документы | 5/5 | 25,9 | 39,7 |
| E | вне базы, отказ | 3/3 | 0 | 0 |
| F | дообучение через эксперта | 2/2 | 3,6 | 6,8 |
| G | проверка чисел | 2/3 | 19,5 | 62,3 |
| Итого | | 30/31 | медиана 16,0 | |

Единственный провал, G03 (два числа из пресейла ДИБ: 10 заявок и 6 месяцев): маленькая модель взяла для второго числа п. 8.4 вместо п. 8.3 и сформулировала ответ невнятно. Число 6 в п. 8.4 есть, поэтому проверка чисел её не остановила. Это ограничение модели 3B; с более сильной моделью результат нужно проверять отдельно.

Время ответа определяется в основном LLM на процессоре. Ответы без модели (отказ вне базы, разъяснение из базы) укладываются в доли секунды; уточнение подразделения тоже без обращения к генерации. Ответ «по дирекциям» вызывает модель по разу на каждую дирекцию, поэтому он в 2–3 раза дольше обычного.

## 4. Локальная модель для стенда (Ollama)

GigaChat API используется только при разработке: он требует выхода в сеть Сбера и ключ, а регламенты в запросах уходят наружу. Для стенда заказчика модель нужно запускать локально через Ollama (`LLM_PROVIDER=ollama`, `OLLAMA_BASE_URL`, `OLLAMA_MODEL`).

Что проверено: `qwen2.5:3b-instruct` (около 2 ГБ, 4-битное квантование) работает на процессоре, ответ на русском формально правильный, JSON с цитатами возвращает стабильно, но формулировки грубые, а на вопросах с двумя числами ошибается (см. G03). Для демонстрации перед жюри этого хватает, для работы сотрудников нужна модель крупнее.

Что не проверено нами, оценки ориентировочные и зависят от квантования: 7B-модели класса Qwen2.5-7B-Instruct в 4-битном виде занимают около 5 ГБ, 14B около 9 ГБ, 32B около 20 ГБ; сверх весов нужно 1–3 ГБ на контекст 8192 токенов (`OLLAMA_NUM_CTX`). Качество на регламентах предстоит сравнить прогоном `eval_softline.py`, прежде чем выбирать.

Минимальные требования стенда:

| Часть | Требование |
|---|---|
| Поиск (e5 + реранкер) | около 4 ГБ ОЗУ или видеопамяти под обе модели, 3 ГБ диска на веса; работает и на процессоре |
| LLM 3B (проверено) | процессор от 8 потоков, 8 ГБ ОЗУ; ответ 6–25 с |
| LLM 7B | ориентир: GPU от 8 ГБ видеопамяти или процессор с 16 ГБ ОЗУ и ответом порядка десятков секунд |
| LLM 14B | ориентир: GPU 16–24 ГБ видеопамяти |
| Параллельность | `LLM_MAX_CONCURRENCY` (по умолчанию 2) запросов к модели на процесс |

Рекомендация к выбору сервера: для демонстрации хватит сервера без GPU с 8 vCPU и 16 ГБ ОЗУ и моделью 3B (то, на чём получены цифры выше). Для стенда, которым будут пользоваться люди, разумнее сервер с одной GPU на 16–24 ГБ видеопамяти и моделью класса 7B–14B; конкретные модель и конфигурация фиксируются после прогона тестового набора на выбранной машине.

Для продакшн-контура как вариант можно рассмотреть открытую GigaChat 4 708B-A41B (лицензия MIT); ресурсы под неё на порядки больше и в этом документе не оценивались. Младшая GigaChat 4 37B-A4B выпущена под некоммерческой лицензией для частных лиц, поэтому для проекта заказчика она подходит только для личных экспериментов.

## 5. Стоимость одного вопроса: методика

Цены не вписаны: они заполняются после выбора сервера и тарифа. Допущения явные.

Измерено в прогоне раздела 3 (27 вопросов, дошедших до модели): в среднем 1281 токен запроса и 168 токенов ответа, то есть около 1450 токенов на вопрос. Токенайзеры GigaChat и Qwen различаются, поэтому для облачного расчёта число нужно перемерить на GigaChat. Вопросы, закрытые без модели (отказ вне базы, разъяснение из базы, уточнение подразделения), токенов не тратят: в тестовом наборе это 4 вопроса из 31 без учёта повторов; доля `s` определяется по реальному потоку вопросов.

Обозначения: `T` — токенов на вопрос к модели; `P` — цена 1000 токенов по тарифу, руб.; `S` — стоимость сервера в час, руб.; `t` — среднее время ответа модели на вопрос, с; `k` — число одновременных запросов (`LLM_MAX_CONCURRENCY`); `u` — доля времени, когда сервер занят вопросами (загрузка); `s` — доля вопросов, дошедших до модели.

- Облачная модель: `C = s * T / 1000 * P`.
- Локальная модель на выделенном сервере: пропускная способность `N = 3600 * k / t` вопросов в час при полной загрузке, стоимость `C = s * S / (N * u)`. Чем ниже загрузка, тем дороже каждый вопрос; для демонстрации `u` близка к нулю и считать нужно стоимость стенда в сутки, а не вопроса.
- Добавки: поиск (эмбеддинги и реранкер) на том же сервере уже входит в `S`; хранение и трафик не учтены.

Админка считает `C` по текущему потоку: задаются `LLM_PRICE_PER_1K_TOKENS` (`P`) и `STAND_COST_PER_HOUR` (`S`), токены и время берутся из журнала.

| Вариант | `P`, руб./1000 токенов | `S`, руб./час | `t`, с | `k` | `C`, руб. |
|---|---|---|---|---|---|
| GigaChat API (только разработка) | заполнить по тарифу | не применимо | | | |
| Локальная 3B, процессор | не применимо | заполнить после выбора сервера | около 16 | 2 | |
| Локальная 7B–14B, GPU | не применимо | заполнить после выбора сервера | измерить | | |

## 6. Агентность

Это не автономный агент с набором инструментов, а фиксированный конвейер с циклом «подумать, сделать, проверить» и несколькими решениями по ходу. Каждый шаг виден в ответе в блоке «Ход работы».

1. Проверки до поиска: фильтр лексики; вопрос вне базы (маржа, премии, просьбы составить документ); поиск в базе разъяснений службы качества; расширение запроса по глоссарию.
2. Решение о подразделении: явное в вопросе, из сессии, уточнение кнопками или ответ по всем дирекциям отдельно.
3. Поиск и оценка: гибридный поиск (e5, BM25), реранкер, пороги `CONFIDENT_THRESHOLD` и `UNCERTAIN_THRESHOLD`.
4. Цикл: при неуверенном результате запрос переформулируется (правилами или моделью) и поиск повторяется не больше `AGENT_MAX_REWRITES` раз.
5. Ответ и самопроверка: цитата должна дословно найтись в пункте, числа и даты ответа должны быть в цитируемых пунктах, противоречие пунктов отмечается моделью; не прошло проверку — показывается дословный пункт или варианты.
6. Действие: письмо в службу качества, если ответа нет, пункты противоречат друг другу или уверенность низкая; ссылки на отсутствующие в базе документы называются прямо.
7. Обучение: ответ эксперта попадает в базу разъяснений, повторы копятся и подсвечивают регламенты на пересмотр.

## 7. Ограничения

- GigaChat с машины разработчика проверить не удалось: сетевой доступ к серверам Сбера из-за настроек VPN был закрыт. Цифры раздела 3 получены на Ollama с моделью 3B; качество выжимок на GigaChat нужно измерить отдельно.
- Отправка через SMTP и чтение через IMAP проверены тестами с подставными серверами, но не на реальной почте. По умолчанию письма только складываются в `data/runtime/outbox`; адреса службы качества и сотрудника в `.env` тестовые.
- Профиль сотрудника имитируется (`DEMO_USER_EMAIL`, `DEMO_USER_NAME`), настоящей авторизации и справочника сотрудников нет. Контакты ответственных по дирекциям в `boxes_softline.csv` — заглушки.
- Подразделение определяется по названиям файлов (`doc_patterns`) и словам в вопросе (`aliases`); при другой схеме именования файлов эти правила надо поправить.
- Порог похожести для базы разъяснений (`FAQ_SIMILARITY` и соседние) подобран по небольшому числу примеров; на большом потоке возможны как промахи, так и ложные совпадения.
- Автоматическая оценка прогона грубая (режим, пункт, ключевые числа); полноту и тон ответов нужно просматривать глазами.
- Распознавание «ссылок на отсутствующие документы» основано на шаблонах русских названий («регламент …», «положение …») и проверено на четырёх выданных документах.
- Веб-интерфейс и бот проверены вручную и тестами в объёме, указанном в репозитории; нагрузочных испытаний не было.
