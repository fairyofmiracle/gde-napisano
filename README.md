# Где написано?

Ответы на вопросы по корпоративным документам **со ссылкой на конкретный пункт**.

Вопрос → поиск по пунктам (эмбеддинги + реранкер) → ответ модели только по найденному тексту → в ответе ссылка вида «п. 3.2 Регламента…». Есть веб-интерфейс, админка, операторская и Telegram-бот (текст и голос).

Для кейса Softline (регламенты ДБРЦТ, Дирекции ИБ и Технической дирекции) добавлены уточнение подразделения, письма в службу качества, база разъяснений экспертов, глоссарий и аналитика. Подробности и ограничения: [docs/softline.md](docs/softline.md).

## Возможности

- Разбор документов на пункты: `.docx`, `.doc`, `.pdf`, изображения (OCR), `.txt`/`.md`, `.rtf`, `.odt`, `.xlsx`, `.html`
- Поиск: `multilingual-e5-base` + реранкер `bge-reranker-v2-m3`, пороги уверенности и предупреждение при неоднозначности
- LLM: **Ollama** (по умолчанию) или **GigaChat**
- Переформулировка неуверенного запроса, сверка чисел/дат с текстом пункта
- Отзывы и кейсы «как решили на практике» (с модерацией в операторской)
- Админка: загрузка документов, доступ по токену, IP-фильтрам и rate limit
- Telegram-бот: текст и голосовые (GigaAM или Whisper)
- Уточнение подразделения, письма в службу качества, база разъяснений, фильтр вопросов вне регламентов, глоссарий, аналитика (см. ниже)
- Кнопка «Не понял»: тот же ответ простыми словами, цитаты и номера пунктов не меняются
- Отчёт «Где не написано?»: вопросы без ответа, противоречия, ссылки на документы вне базы

## Быстрый старт (локально)

### 1. Окружение

```powershell
python -m venv .venv
.\.venv\Scripts\activate
pip install -r requirements.txt
```

Варианты зависимостей:

| Файл | Когда |
|------|--------|
| `requirements.txt` | Полное приложение (модели, поиск, API) |
| `requirements-ui.txt` | Только UI без torch/моделей (`DEMO_UI_ONLY=true`) |
| `requirements-bot.txt` | Telegram-бот + распознавание речи |
| `requirements-dev.txt` | Полный набор + pytest и тестовые утилиты |

Системные утилиты по необходимости:

- **Tesseract** (`rus+eng`) — OCR для сканов и картинок; на Windows при необходимости задайте `TESSERACT_CMD`
- **LibreOffice** (`soffice`) — конвертация `.doc` → `.docx`; при необходимости `SOFFICE_CMD`
- **Ollama** — если `LLM_PROVIDER=ollama` (модель по умолчанию `qwen2.5:3b-instruct`)

### 2. Конфиг

```powershell
copy .env.example .env
```

Минимум для начала работы:

1. Сгенерируйте токен админки (без него загрузка документов и операторская закрыты):

   ```powershell
   python -c "import secrets; print(secrets.token_urlsafe(24))"
   ```

   Впишите в `ADMIN_TOKEN` (не короче `ADMIN_TOKEN_MIN_LENGTH`).

2. Проверьте пути: `DATA_DIR`, `DOCS_DIR`, `QDRANT_PATH` (локально Qdrant работает из папки, сервер не обязателен).
   Документы кладите в `DOCS_DIR` (по умолчанию `data/runtime/docs`) или задайте свой путь. Пример ящиков: `copy examples\boxes.csv data\boxes.csv`. Для кейса Softline: `copy examples\boxes_softline.csv data\boxes.csv` и `copy examples\glossary.tsv data\glossary.tsv`.

3. При GigaChat: `GIGACHAT_CREDENTIALS` и сертификат — см. [certs/README.md](certs/README.md).

Полный список переменных — в `.env.example` с комментариями.

### 3. Запуск

Приложение собирается фабрикой, поэтому команда с `app_factory --factory` (вариант `app.main:app` не запустится):

```powershell
# API и веб-интерфейс: http://127.0.0.1:8010, админка: /admin
python -m uvicorn app.main:app_factory --factory --host 127.0.0.1 --port 8010

# Telegram-бот (нужны TELEGRAM_BOT_TOKEN и запущенное приложение по адресу DOCAGENT_URL)
python -m bot
```

Первый запуск скачивает модели поиска (около 3 ГБ) и индексирует документы из `DOCS_DIR`; пока идёт индексация, `/api/health` показывает `indexing: true`.

Проверка тестов:

```powershell
pip install -r requirements-dev.txt
pytest
```

Прогон тестовых вопросов кейса по настоящим моделям (данные пишутся во временную папку, письма не отправляются):

```powershell
python scripts\eval_softline.py --docs data\docs --questions eval\test_questions.json --out eval
```

## Docker (когда появятся compose-файлы)

В `.env.example` уже заложен публичный стенд:

- `PUBLIC_BIND` — `127.0.0.1` только с сервера, `0.0.0.0` — снаружи
- `SITE_ADDRESS` — домен для HTTPS (Let's Encrypt) или пусто для HTTP на порту 80
- профиль бота: `docker compose --profile bot up -d --build`

В образе приложения лежат зависимости из `requirements.txt`; бот собирается отдельно (`requirements-bot.txt`).

## Как пользоваться

1. Откройте веб-интерфейс, задайте вопрос обычным языком.
2. В ответе будет формулировка **и** ссылка на пункт документа.
3. В админке (с `ADMIN_TOKEN`) загрузите/обновите документы — индекс перестроится.
4. В операторской можно разбирать неуверенные ответы и одобрять практические кейсы.
5. В Telegram тот же поиск: текст или голосовое (если включён `TRANSCRIBER`).

На демостенде я оставила бота открытым для всех: документы в нём обезличены. В продуктиве доступ закрывается списком `TELEGRAM_ALLOWED_USERS` (Telegram id сотрудников) и `TELEGRAM_ALLOWED_CHATS` для групп; по умолчанию `TELEGRAM_OPEN=false`. Частота запросов ограничена: 30 в минуту, голосовые — 3 в минуту.


## Программный интерфейс (API)

FastAPI отдаёт интерактивную схему на стенде:

- Swagger UI: http://109.172.90.198/docs
- ReDoc: http://109.172.90.198/redoc
- машинное описание OpenAPI 3.1: http://109.172.90.198/openapi.json

Я проверила 28.11.2026: все три адреса отвечают 200. Локально те же пути — `/docs`, `/redoc`, `/openapi.json`.

Публичные методы (чат, хранилище регламентов, ящички, отзывы, служебные) токена не требуют. Загрузка и удаление документов, переиндексация, статистика, аналитика и операторская закрыты токеном администратора (`Authorization: Bearer` или заголовок `X-Admin-Token`).

Основные эндпоинты (из `/openapi.json`):

- Служебное: `GET /health`, `GET /ready`, `GET /version`, `GET /api/health`.
- Чат и поиск: `POST /api/chat` (задать вопрос), `POST /api/chat/stream` (тот же запрос, ответ по шагам), `POST /api/escalate` (передать в службу качества), `POST /api/simplify` (пересказать ответ простыми словами).
- Документы и пробелы: `GET /api/wiki`, `GET /api/wiki/export`, `GET /api/gaps`, `GET /api/documents/{doc_id}/clauses`, `GET /api/clauses/{point_id}`. Загрузка, список, удаление и переиндексация — `/api/admin/documents`, `/api/admin/upload`, `/api/admin/reindex`.
- Отзывы и практика: `POST /api/feedback`, `POST /api/practice`, очередь оператора `/api/operator/inbox`.
- Служба качества и аналитика: заявки `/api/operator/escalations` (ответ эксперта, импорт `.eml`), демо-почта `/api/operator/mail`, база разъяснений `/api/operator/faq`, сводка `/api/admin/stats`, аналитика `/api/admin/analytics`.
- Справочник подразделений: `GET /api/boxes`.

Пример вопроса:

```bash
curl -sS -X POST http://109.172.90.198/api/chat \
  -H 'Content-Type: application/json' \
  -d '{"question":"По каким направлениям TPS самостоятельно валидирует спецификацию в Технической дирекции?"}'
```

## Ход работы

Под каждым ответом свёрнут блок «Ход работы» из трёх частей. Всё в нём берётся из шагов конвейера, ничего не дописывается отдельно.

- **Улики**: какие пункты нашлись, какие вошли в ответ, у каждого ссылка на пункт в хранилище и оценка реранкера.
- **Сверка**: порог уверенности, дословность цитаты, числа и даты, противоречия, какие пункты согласуются или расходятся, чего нет в базе.
- **Вердикт**: ответ, дословный пункт, противоречие, «не написано» или передача в службу качества, с уровнем уверенности и причиной.

Подробные шаги со временем лежат внутри блока («Все шаги»). В API то же самое приходит в поле `investigation`, в Telegram по строке на часть в конце ответа.

## Ответ по шагам

На сайте ответ появляется по частям: сначала текущий шаг («Ищу в документах», «Сверяю найденные пункты», «Пишу ответ»), затем найденные пункты с цитатами, потом текст ответа по мере того, как модель его пишет. Проверка цитат, чисел и противоречий идёт после генерации, и итоговый ответ заменяет черновик: если проверка показала расхождение или число не из документа, вместо черновика будет дословный пункт или оба противоречащих пункта.

- `POST /api/chat/stream` принимает то же, что `/api/chat`, и отдаёт поток NDJSON: `status`, `evidence`, `draft`, `ping` раз в 10 секунд, в конце `final` с ответом в формате `/api/chat`. Обычный `/api/chat` работает как раньше.
- Telegram-бот пока готовит ответ показывает «печатает…» и присылает одно итоговое сообщение с ответом, цитатой и источником, без сообщений о ходе работы. Для голосового первой строкой идёт «Вопрос: …» с расшифровкой, подтверждать её не нужно. Короткие реакции вроде «да» или «спасибо» в поиск не уходят и заявок не создают.
- Поток идёт напрямую из uvicorn без буферизации (`X-Accel-Buffering: no` на случай прокси). Ожидание ответа не ограничено по времени на сайте, у бота таймаут чтения 180 секунд, а `ping` не даёт соединению простаивать.

Переформулировка вопроса отдельным вызовом модели делается только в «серой зоне»: лучшая оценка не ниже `AGENT_REWRITE_LLM_MIN_SCORE` (по умолчанию 0,25), вопрос короткий (до 4 слов) или ссылается на прошлый разговор. Если подходящих пунктов не видно совсем, хватает правил переформулировки. `AGENT_REWRITE_LLM_MIN_SCORE=0` возвращает прежнее поведение.

## Уточнение подразделения

Если в вопросе не названо подразделение, а подходящие пункты нашлись в регламентах нескольких дирекций, бот не выбирает сам и не усредняет сроки. Он задаёт один уточняющий вопрос с кнопками (веб и Telegram), не больше `CLARIFY_MAX` раз за сессию. Выбор запоминается в сессии (`session_id`). Ответ «не знаю» показывает варианты каждой дирекции отдельно, каждый со своими пунктами. Если дирекция названа в самом вопросе, уточнения нет. Подразделения, названия файлов и слова-подсказки задаются в `data/boxes.csv` (столбцы `doc_patterns` и `aliases`, образец: `examples/boxes_softline.csv`).

## Письма в службу качества

Если ответа нет, найденные пункты противоречат друг другу или уверенность низкая, бот формирует письмо на `QUALITY_EMAIL`: вопрос, что нашлось, причина. Сотрудник (`DEMO_USER_EMAIL`, имитация профиля) стоит в копии. Если `SMTP_HOST` пуст, письмо сохраняется в `DATA_DIR/outbox` как `.eml` и видно в админке; реальная отправка включается заданием `SMTP_*`. Тот же вопрос в той же сессии второй раз не отправляется. Сотрудник может сам передать вопрос кнопкой «Передать вопрос в службу качества» (`POST /api/escalate`).

На стенде письма наружу не отправляются. Их видно в демо-ящике службы качества `/mail` (ссылка «Почта» для ролей эксперта и администратора, данные под `ADMIN_TOKEN`): список писем с номером заявки ГН-N, темой, датой и отметкой «прочитано», открытое письмо с вопросом и найденными пунктами со ссылками, кнопка «Ответить / добавить разъяснение» ведёт в раздел службы качества в админке.

В продуктиве письма уходят через SMTP-сервер компании или Exchange (через его SMTP-приём), ответы экспертов читаются по IMAP. Всё задаётся в `.env`, по умолчанию выключено:

```
SMTP_HOST=mail.company.local      # пусто — только outbox и демо-ящик
SMTP_PORT=587
SMTP_USER=...
SMTP_PASSWORD=...
SMTP_FROM=gde-napisano@company.local
SMTP_ALLOWED_RECIPIENTS=          # необязательно: настоящие письма только на эти адреса (для пилота)
QUALITY_EMAIL=quality@company.local
IMAP_HOST=... IMAP_USER=... IMAP_PASSWORD=...
```

При ошибке SMTP письмо сохраняется в outbox, ответ сотруднику не ломается. Проверка настройки: `python scripts/send_test_email.py <адрес из SMTP_ALLOWED_RECIPIENTS>`. На VDSina исходящие порты 25, 465 и 587 закрыты провайдером, поэтому на этом сервере нужен почтовый сервис с портом 2525 или открытие портов через поддержку.

Вопросы про маржу, премии, просьбы составить письмо или анализ и разговор не по делу получают отказ без поиска и без письма. Если регламент ссылается на документ, которого нет в базе (например, «Регламент подбора субподрядчика»), бот называет его и прямо говорит, что содержания не знает.

## Разъяснения службы качества

Ответ эксперта попадает в базу разъяснений тремя способами: форма в админке, импорт письма `.eml` или чтение почты по IMAP (`IMAP_*`, кнопка «Проверить почту»). Заявка находится по метке `[ГН-номер]` в теме. Ответ, начинающийся с «ОТВЕТ:» или не оканчивающийся вопросом, считается финальным и попадает в базу; письмо с «ВОПРОС:» только сохраняется. Следующий похожий вопрос получает этот ответ с пометкой «Разъяснение службы качества» и датой. Сами регламенты не изменяются. Если разъяснение выдано `REVIEW_REPEAT_THRESHOLD` раз, в админке появляется сигнал «пересмотреть регламент».

## Аналитика

В админке (раздел «Аналитика»; API: `GET /api/admin/analytics`): неудачные поиски и эскалации, повторяющиеся вопросы, самые частые документы и пункты в ответах, сигналы к пересмотру регламентов, время ответа (медиана, p95) и оценка стоимости вопроса. Оценка стоимости считается по `LLM_PRICE_PER_1K_TOKENS` и `STAND_COST_PER_HOUR`; пока они равны 0, показывается число токенов без цены.

## Агент-проверяющий

Второй агент со своей ролью и своим промптом. Когда основной конвейер дал уверенный ответ с проверенной цитатой, проверяющий отдельным вызовом модели получает вопрос, готовый ответ и пункты, на которые ответ ссылается, и возвращает строгий JSON-вердикт:

- `ok` — ответ подтверждён пунктами, уходит сотруднику как есть;
- `retry` — пункты не о том: проверяющий даёт новую поисковую формулировку, конвейер один раз ищет и отвечает заново (не больше одной итерации). Если повтор не дал проверенного ответа, остаётся исходный;
- `escalate` — ответ расходится с пунктами: ответ и цитаты остаются видны, а вопрос уходит в службу качества обычным путём эскалации (заявка ГН, причина «проверяющий агент не подтвердил ответ»).

Шаг «Проверяющий агент» пишется в ход работы на сайте и в API (поле `verifier`). В Telegram промежуточных сообщений нет. Ошибка, таймаут (по умолчанию 6 с) или невалидный JSON проверяющего ничего не ломают: сотрудник получает исходный ответ, причина пишется в лог. Работает с обоими провайдерами (`gigachat` и `ollama`).

Включение: `VERIFIER_ENABLED=true`, таймаут — `VERIFIER_TIMEOUT` (секунды). По умолчанию выключен.

Цена: +1 вызов модели на уверенный ответ. По замерам на стенде (GigaChat Lite, 7 вызовов) в среднем 342 токена на входе и 27 на выходе, около 0,3 с. При тарифе из расчёта (53,28 ₽ за 1 млн токенов без НДС) это примерно +0,02 ₽ к уверенному ответу (0,037 → ~0,057 ₽). Прогон 31 тестового вопроса Softline с проверяющим: 31/31, медиана 10,0 с.

## Модель: GigaChat на стенде и локальный режим

Сейчас стенд отвечает через GigaChat API (`LLM_PROVIDER=gigachat`): ответ занимает около 10 с (медиана прогона 31 вопроса 9,6 с, прошло 31 из 31). Регламенты при этом передаются во внешний сервис.

Закрытый контур поддерживается и включается одной строкой: `LLM_PROVIDER=ollama` в `.env` и перезапуск сервисов. Тогда ответы строит локальная модель `qwen2.5:3b-instruct` через Ollama, поиск (эмбеддинги и реранкер) в любом режиме работает на сервере, при `HF_HUB_OFFLINE=1` без выхода в сеть. Что я измерила на сервере 4 vCPU / 8 ГБ без GPU: ответ строится 60–170 с (разбор запроса моделью на таком процессоре идёт около 20 токенов в секунду, генерация около 5), часть вопросов формулируется грубо. Для живого использования в закрытом контуре нужны больше ядер или GPU. На 8 vCPU тот же набор давал медиану около 16 с.

Что ещё не доделано:

- скорость локальной модели (нужно железо, а не настройки);
- противоречия внутри одного документа ищутся по предложениям, близким к вопросу, и могут быть пропущены, если пункт далеко от вопроса по смыслу;
- G03: на локальной модели ответ на вопрос из двух частей иногда формулируется неточно, числа при этом проверяются по тексту пунктов;
- хранилище: я добавила страницу `/wiki` со списком загруженных регламентов и разъяснениями службы качества; выгрузки из Confluence нет, файлы по-прежнему лежат в папке;
- вход и роли имитируются (сотрудник, эксперт службы качества, администратор): роль меняет набор видимых разделов, доступ к `/admin` по-прежнему закрыт токеном; настоящей авторизации и разграничения прав нет.

## Служба качества без внешней почты

Если `SMTP_HOST` пуст, письма в службу качества не уходят наружу, а складываются в `data/runtime/outbox` как `.eml`. Каждый запрос получает номер (в ответе: «Номер заявки: ГН-N») и виден в `/admin`, раздел «Служба качества»: вопрос, причина, кому и в копии кому, найденные пункты. Эксперт пишет ответ в форме рядом с заявкой, ответ попадает в базу разъяснений, и повторный такой же вопрос получает его как «Разъяснение службы качества». Регламенты при этом не меняются. Для проверки на демонстрации: задать вопрос вне регламентов, открыть `/admin`, ответить на заявку, задать вопрос ещё раз.

Вход на главной странице («Войти») имитирует корпоративную учётную запись: имя и почта идут в письмо в службу качества, роль определяет, какие ссылки и разделы показаны.

## Если модель недоступна

После `LLM_BREAKER_FAILURES` сбоев подряд модель на `LLM_BREAKER_COOLDOWN` секунд считается недоступной: вопросы не ждут таймаутов, бот показывает дословный пункт со ссылкой. Если реранкер оценил первый пункт не ниже `QUOTE_FALLBACK_SCORE`, а модель ответила «ответа нет», пункт тоже показывается дословно.

## Модели с размышлениями (Qwen3)

Модели семейства Qwen3 по умолчанию сначала «размышляют» вслух, это долго и ломает формат ответа. `OLLAMA_THINK=false` передаёт в Ollama `think: false`. Если сервер Ollama этот параметр не принимает, в системный промпт добавляется `/no_think`. Блоки `<think>…</think>` в любом случае вырезаются из ответа, в том числе при выводе по шагам. Для qwen2.5 и GigaChat настройку можно не задавать.

## Дальнейшее развитие

Видео и картинки на стенде не подключены: работаю только с четырьмя выданными регламентами. Что планирую добавить:

- **Видео.** Расшифровка речи через GigaAM с таймкодами, нарезка на смысловые фрагменты по 30–90 с. В ответе цитата с таймкодом, ссылка открывает плеер с нужной секунды, рядом полная расшифровка.
- **Картинки и схемы.** Текст с изображения через OCR (Tesseract, модуль `app/parsing/ocr.py` уже есть) и краткое описание. Отдельный тип источника «рисунок», сам рисунок показывается в ответе.

Оба типа добавляются как новые фрагменты без переиндексации, поэтому ссылки на существующие пункты не меняются.


## Стоимость владения

Цифры — из расчёта [docs/cost_calculation.xlsx](docs/cost_calculation.xlsx), все суммы в рублях без НДС.

На стенде (GigaChat Lite через API) токены стоят 0,041 ₽ за вопрос в среднем: 0,037 ₽ за ответ и 0,004 ₽ за агента-проверяющего (он вызывается только на уверенных ответах; к такому ответу добавляет 0,02 ₽). С арендой сервера стенда (VDSina, 80 ₽ в сутки) получается 0,20 ₽ за вопрос при 500 вопросах в сутки и 0,081 ₽ при 2000.

Закрытый контур (лист «Локальная модель»): плата за токены равна 0, стоимость — аренда. На текущем 4 vCPU без GPU Qwen2.5-1.5B отвечает с медианой 50,9 с (0,16 ₽ за вопрос при 500 в сутки и 0,08 ₽ при 2000); Qwen3-1.7B — медиана 97,8 с (0,16 ₽ и 0,12 ₽). Для живой работы это непригодно. Оценка железа для ответа около 10 с — один GPU уровня L4 или RTX 4090; на стенде я это не измеряла. Ориентир аренды: облачный L4 — 2,75 ₽ за вопрос при 500 в сутки и 0,69 ₽ при 2000; выделенный RTX 4090 — 3,11 ₽ и 0,78 ₽. Подробности, тарифы и сравнение моделей — в том же файле, листы «Содержание», «Расчёт», «Локальная модель» и «Сравнение».
